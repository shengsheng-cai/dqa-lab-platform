# QA 文件與缺陷案例規則

## 三種紀錄不要混在一起

- `CLAUDE.local.md` 的待補是內部工作清單，可包含功能缺陷、UX、文案、可存取性與重構建議。
- 一般修正由待補／Issue（若有）、commit 或 PR，以及相稱的測試留下可追蹤證據。
- `docs/qa/BUG-*.md` 是作品集中精選的缺陷案例，不是完整缺陷資料庫，也不是每次修正的必要產物。

## 何時才建立獨立缺陷案例

只有同時符合以下條件時，才考慮新增 `BUG-*.md`：

1. 有可重現的使用者或系統影響，不只是偏好、文案、版面或未來重構。
2. 影響核心風險，或能展示與既有案例不同的 QA／工程判斷。
3. 有修正前證據或可核對的歷史證據，並有相稱的回歸保護。
4. 不與既有案例重複；同一缺陷類型的延伸優先補進既有案例或只留在測試與 Git 歷史。

符合條件仍不代表必須新增。建立前要先說明案例價值並取得使用者明確同意；編號只在同意後配發。

## 誠實記錄時序

- 報告必須明示是修正前記錄、與修正同時整理，或修正後依證據回顧；Git 歷史無法證明的先後順序不得宣稱為事實。
- 「記錄」可以是待補、Issue、commit／PR、測試或獨立缺陷案例，不等於一定要新增 Markdown。
- Severity 描述影響，Priority 描述處理順序；兩者都不直接決定要不要成為作品案例。

## README 與追溯表

- README 只展示少數最有代表性的案例，完整資料留在 `docs/qa/`，不以報告數量當成果。
- 追溯表連的是需求、風險與測試；「缺陷證據」是可選欄位，沒有獨立案例時填 `—`。
- 測試策略與風險計畫不得要求每個已修正缺陷都建立或連結獨立報告。
- QA 文件維持中英雙語；改一份就同步另一份，並跑文件翻譯同步測試。
