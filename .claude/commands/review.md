請審查目前的修改，只回報問題，不直接修改檔案。

步驟：

1. 執行 `git status --short`，列出已追蹤與未追蹤的修改；未追蹤的新檔案也要實際讀取，不能只看 `git diff`。
2. 執行 `git diff --stat`、`git diff` 與 `git diff --staged`，確認完整改動。依照本次需求判斷哪些屬於本次修改；無法確認的既有修改標示為「範圍不明」，不得擅自改動或還原。
3. 依改動範圍讀取相關規則，不要固定只看單一檔案（下面是路徑，用到才讀，不要整批載入）：
   - API、權限、交易、排程、治具借還、稽核埋點或 LINE：`.claude/rules/api-conventions.md`
   - 設備狀態、模擬流程或採購單狀態：`.claude/rules/state-machine.md`
   - 前端元件或版面：`.claude/rules/frontend.md`
   - 測試、測試方式，或動到 `models.py` 與資料庫 schema：`.claude/rules/testing.md`
4. 逐一檢查：
   - 是否混入與本次需求無關或非預期的修改
   - 是否遺留 TODO、debug print、假資料、憑證或敏感資訊
   - 新增或修改的 API 是否符合權限與 API 慣例
   - 狀態轉換、交易邊界與前端佈局是否符合相關規則
   - 行為改動是否有相稱的回歸測試；若沒有可信的本次測試結果，執行相關測試並回報結果
   - 文件、測試與實際行為是否一致。這條要看**整份 repo 的對外說明**，不只 `.claude/rules/`：
     `README.md`、程式碼註解、docstring 只要描述到這次改掉的行為，就一起核對有沒有脫節
   - 這次做的是不是當初講好的那件事：有沒有少做、有沒有偷加沒要求的東西
5. 只列出有具體證據的問題，依影響由高到低排列。每項包含：
   - `檔案:行號`
   - 觸發條件與使用者影響
   - 建議修法
   - 是否屬於本次修改
6. 若沒有問題，說「未發現問題」，並簡短列出已檢查範圍與尚未驗證的部分，不要只說「看起來沒問題」。
7. 本次範圍外的問題先向使用者報告；未取得明確同意前，不加入 `CLAUDE.local.md` 的「待補」。
8. 回報審查結果後停止；除非使用者另外要求，不主動詢問或執行 commit。
