## 摘要

同一個來源位址連續五次認證失敗，就會被鎖十分鐘。但部署上的每個請求都經過平台的
轉送層，而容器啟動時沒有告訴 uvicorn「前面那層是自己人」，於是不論誰來，
`request.client.host` 都解析成轉送層自己的內網位址。一個計數器代表了所有人。

任何人失敗五次就夠了——公開的 Space 會被掃描，而沒帶憑證去打 `/api/` 的請求也算在
內——接下來十分鐘，所有訪客都會收到 429。這包括手上已經有有效訪客憑證的人，因為
封鎖檢查排在驗證憑證之前；也包括登入端點本身，它同樣先看封鎖狀態才看密碼。

程式沒有任何一處行為出錯。門檻、計數、封鎖時間都照設計運作。壞的是它們據以計數的
那個 key，根本認不出任何人。

## 受影響的路徑

| 路徑 | 錯誤行為 |
|---|---|
| `Dockerfile` — 容器啟動指令 | 用 `uvicorn app.main:app` 起服務，沒有 `--forwarded-allow-ips`，於是 uvicorn 退回只信任 `127.0.0.1`，`X-Forwarded-For` 被整個忽略 |
| `backend/app/auth.py` — `login`、`demo_login`、`auth_middleware` | 三處都讀 `request.client.host` 當鎖定的 key；在不受信任的轉送層後面，那個值是所有人共用的一個常數 |
| `.github/workflows/test.yml` | 不 build image，所以那行啟動指令從來沒有任何自動化流程執行過，也就沒有東西看得到這件事 |

## 前置條件

- 容器前面有反向代理的部署環境。HF Space 是這種；本機與 E2E 不是，這正是這個缺陷
  在開發階段完全看不出來的原因。
- uvicorn 啟動時既沒有 `--forwarded-allow-ips`，也沒有設 `FORWARDED_ALLOW_IPS`
  環境變數——容器當時就是這樣。
- 任何累積得出五次認證失敗的來源。不需要帳號：`auth_middleware` 對「打 `/api/*`
  但完全沒帶憑證」的請求也計數，而那正是未認證掃描的樣子。

## 修正前版本的重現步驟

1. 切到修正 commit 之前的版本。
2. 照容器當時的方式啟動後端，不設定任何代理信任：
   `uvicorn app.main:app --host 0.0.0.0 --port 7860`。
3. 送出五次失敗登入，每次帶不同的 `X-Forwarded-For` 位址，模擬轉送層後面的五個訪客。
4. 再從第六個、先前沒出現過的位址送一個請求。

## 預期結果

每個位址各自累積自己的失敗次數。第六個訪客什麼都沒失敗過，應該按自己這筆請求的
內容得到答覆：密碼錯就 401，密碼對就登入成功。鎖定只鎖到把它累積出來的那個位址。

## 實際結果

第六個訪客收到 429 與「錯誤次數過多，封鎖 10 分鐘」，而它什麼都沒做；接下來十分鐘
所有訪客都一樣。任何打到 `/api/*` 的請求都在憑證被檢查之前就被拒絕，所以正在用系統
的訪客會在操作到一半時被切斷，而且沒辦法靠登入頁回來。

## 證據

- **容器實際看到的來源位址。** 2026-09-07 送往 Space 的一筆探測請求，在容器日誌裡的
  來源位址落在 `10.0.0.0/8`——那是平台的轉送層，不是呼叫端。
- **為什麼會用那個位址。** 在釘住的 uvicorn（0.51.0）裡，`Config.__init__` 會把
  `forwarded_allow_ips=None` 解析成 `os.environ.get("FORWARDED_ALLOW_IPS", "127.0.0.1")`，
  而 `ProxyHeadersMiddleware` 只有在連進來的位址落在那份信任清單裡時才改寫來源。
  轉送層不是 `127.0.0.1`，所以 `X-Forwarded-For` 沒有任何人讀。
- **後果，對同一顆釘住的 uvicorn 實際跑出來的結果。** 餵給 `ProxyHeadersMiddleware`
  一筆從代理位址 `10.1.2.3` 進來的請求：

  | 信任設定 | `X-Forwarded-For` | 應用看到的來源 |
  |---|---|---|
  | `127.0.0.1`（修正前的預設） | `203.0.113.9` | `10.1.2.3` |
  | `127.0.0.1`（修正前的預設） | `198.51.100.4` | `10.1.2.3` |
  | `10.0.0.0/8`（本次修法） | `203.0.113.9` | `203.0.113.9` |
  | `10.0.0.0/8`（本次修法） | `198.51.100.4` | `198.51.100.4` |
  | `10.0.0.0/8`（本次修法） | `1.1.1.1, 203.0.113.9` | `203.0.113.9` |
  | `*`（被刪掉的設定當時的值） | `1.1.1.1, 203.0.113.9` | `1.1.1.1` |

  修正前兩個不同訪客收斂成同一個位址，修正後各自分開。最後兩列是「這不是把舊設定
  補回來」的原因，見根因。
- **鎖定拿那個 key 做什麼。** [`auth.py`](../../backend/app/auth.py) 的
  `MAX_ATTEMPTS = 5`、`BLOCK_SECONDS = 600`；封鎖檢查在 `auth_middleware` 最前面、
  兩條憑證分支之前，也在 `login` 最前面、驗證密碼之前。
- **修正後在實際流量裡拍到的同一個缺陷。** 2026-09-08 的容器日誌顯示兩台互不相干的
  掃描機器人 `20.168.95.140` 與 `172.190.109.35`，各自對 `/api/*` 送出兩筆不帶憑證的
  請求、各自收到 `401`。這四筆每一筆都算進鎖定計數。修正前它們會全部落在那個由轉送層
  推導出來、一般訪客也共用的同一個 key 上——距離拒絕所有人只差一次，而這兩台機器
  根本沒打算登入。日誌裡它們現在各自帶著自己的位址，也就只算在自己頭上。
- **沒有取得：** 被鎖住的訪客的畫面截圖。這不是畫面型缺陷——畫面正確地顯示了伺服器
  送出的訊息。真正該留的證據是「計數是綁在哪個位址上」。

## 根因

信任設定在換平台時掉了，而且沒有任何東西留下來能察覺。

`backend/railway.toml` 的啟動指令原本帶著
`--proxy-headers --forwarded-allow-ips='*'`。`13b4b76`（2026-04-16）移除 Railway 時
把整個檔案刪掉。`861248e`（2026-04-24）加進 HF 的 `Dockerfile`，那行啟動指令是重新
寫的，從來沒帶過這個設定。在這兩顆 commit 之間部署目標換了，而這個決定唯一被記錄
過的地方，跟著舊平台一起走了。

中間不會有任何東西紅，是因為沒有東西在看。CI 跑測試但不 build image，所以那行啟動
指令根本沒有自動化的讀者；本機沒有代理，`request.client.host` 本來就是對的，缺陷
顯現不出來。

還有第二層要講清楚，因為它正是「這不只是把刪掉的東西補回來」的理由：**掉了的那份
設定本身就是錯的。** 值是 `*` 時，uvicorn 取的是 `X-Forwarded-For` 最左邊那筆，而
最左邊是呼叫端自己寫的——所以綁在它上面的鎖定，任何送得出標頭的人都能繞開，也能
拿來指定要鎖誰。照原樣補回去，等於把一個認不出任何人的計數器，換成一個由攻擊者
挑選的計數器。本次修法改成指名轉送層實際所在的網段。

這兩層底下是同一個形狀，跟程式碼裡的一樣：「哪個位址代表一個呼叫端」這件事，系統
從來沒有在任何地方命名過。它是三個地方各自 inline 讀取的一個屬性，所以沒有一個
地方能讓它對或錯，也沒有一個明顯的地方可以測。

## 影響

- 只要累積出任何五次認證失敗——來源不拘，包括根本沒打算登入的自動掃描——部署上的
  每個訪客都會被拒絕十分鐘。
- 被拒絕的不只是新登入，還包括已經通過認證的 session。封鎖在憑證之前判斷，所以
  正在使用系統的訪客會開始每一個請求都收到 429，而且沒辦法靠登入頁回來。
- 畫面上看不出原因。訊息說錯誤次數太多——對計數器來說是真的，對讀到它的人是假的。
- 影響範圍有限且會自己好：計數器在記憶體裡，十分鐘後過期，Space 重啟則直接清空。
- 嚴重度評為 Medium，因為這個基線是作品集 Demo，最壞的後果是十分鐘不能用。優先級
  評為 High，因為它就在線上、修它只要一行，而那十分鐘最可能剛好落在連結才剛發給
  別人的時候。

## 解法

容器啟動時指名轉送層所在的網段：

```
uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-7860} --forwarded-allow-ips=10.0.0.0/8
```

`--proxy-headers` 刻意不一起加：在釘住的這版 uvicorn 裡它本來就預設開啟，兩個寫在
一起會讓人以為關鍵是這一對，但從頭到尾缺的只有那份信任清單。

有兩個刻意的選擇：

- **這件事屬於部署，不屬於應用。** 轉送層在哪個網段是部署目標的知識，而且已經變過
  一次——Railway 用的是一個值，這個 Space 需要另一個。在 `main.py` 裡加
  `ProxyHeadersMiddleware` 等於把同一個常數搬進共用的應用程式碼；改用環境變數設定，
  則是把它搬到這個 repo 裡沒有任何測試看得到的地方，而那正是這個缺陷當初的成因。
- **要網段，不要 `*`。** 信任的值必須窄到把公開網際網路排除在外。`*` 和 `0.0.0.0/0`
  都會讓 uvicorn 去讀標頭裡由呼叫端提供的那一端，那比不設更糟：共用的計數器至少是
  對所有人一視同仁地拒絕，而由攻擊者挑選的計數器可以指定鎖住某一個訪客，攻擊者自己
  則繞得開。

`auth.py` 裡那三處 inline 讀 `request.client.host` 沒有動。信任清單設好之後它們是
對的，而給它們一個共用的存取函式，是這次修正不需要的一項認證程式碼改動。

## 驗證

```bash
cd backend && ../venv/bin/python -m pytest tests/test_deploy_config.py tests/test_login_rate_limit.py
```

`tests/test_deploy_config.py` 從 `Dockerfile` 讀出啟動指令，檢查的是那個信任值實際上
會信任誰，而不是它怎麼拼：公網位址不得落在裡面，轉送層的網段必須落在裡面。這個區別
正是重點——只比對字串的話會接受 `0.0.0.0/0`，而它的行為跟這次拒絕的 `*` 一模一樣。
值消失、被加上 `--no-proxy-headers`、或 server 被換成一個收同樣參數卻不接受網段寫法
的，它也都會紅。

`tests/test_login_rate_limit.py` 釘住那個 key 餵養的行為：五次失敗會鎖、封鎖期間連
正確密碼也被拒、成功登入把計數歸零，以及這份報告在講的殺傷範圍——手上有有效憑證的
訪客，會被別人觸發的封鎖擋在外面。兩邊的斷言都做過蓄意破壞驗證：把失敗計數的累加
拿掉，前兩條會紅；把信任值放寬成 `0.0.0.0/0`，部署那支會紅。

測試套件看不到的兩件事，2026-09-08 以三筆送往部署環境的探測確認。探測打的是
`/health`——它在放行清單上，所以這個動作本身不可能鎖到任何人。三筆都被記在同一個
真實公網位址上：

| 探測 | 送出的 `X-Forwarded-For` | 日誌記下的來源 |
|---|---|---|
| `?probe=bug015-plain` | 沒有 | 呼叫端的真實位址 |
| `?probe=bug015-forged-public` | `192.0.2.111` | 呼叫端的真實位址 |
| `?probe=bug015-forged-trusted` | `10.9.9.9` | 呼叫端的真實位址 |

第一列確認平台的轉送層真的位在 `10.0.0.0/8`；它若搬家，這些測試會照樣綠而線上回到
共用一個計數器，所以每次平台有變動都值得重打一次。第三列更尖銳：偽造一個**落在
信任網段之內**的位址，正是「轉送層把呼叫端的標頭原樣傳過來、而不是接在後面」時會
成功的那種攻擊。它沒有成功，所以證據表裡「偽造擋得住」那一列在現實中也成立，不只是
理論上成立。
