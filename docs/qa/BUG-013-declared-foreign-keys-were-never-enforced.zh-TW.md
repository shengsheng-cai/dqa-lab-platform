## 摘要

schema 在十張表上宣告了十五條外鍵，SQLite 一條都沒有理會。

`PRAGMA foreign_keys` 預設是**關的**，而且是每條連線各自設定，所以
`ForeignKey("users.id")` 這樣的宣告在每條連線都打開之前只是註解。而沒有人打開它。
結果不是當掉，是那種安靜的錯：刪一個人會成功，指向他的那些資料則繼續指著一個已經不存在的 ID。

反方向也一樣沒有聲音。借用紀錄可以寫進一個從來不是使用者的借用人，沒有任何東西有意見。

## 受影響的路徑

| 路徑 | 問題 |
|---|---|
| `backend/app/models.py` | 十五條 `ForeignKey(...)` 宣告，全部沒有生效，也都沒說父列被刪時子列該怎麼辦 |
| `backend/app/auth.py` — `delete_user` | 刪掉使用者並寫稽核；沒有清掉五張表、六個欄位裡指向他的 ID |
| `backend/app/schedules.py` — `_delete_schedule_db` | 手動清了 `schedule_fixtures` 與 `fixture_loans.schedule_id`，唯獨沒有 `sop_executions.schedule_id`——刪排程就會讓執行紀錄指向一筆不存在的排程 |
| `backend/app/fixtures.py` — `create_loan` | 直接把 request 送來的 `borrower_user_id` 寫進資料庫，沒查過這個人存不存在 |

## 前置條件

- 資料庫是 SQLite，而且沒有任何連線執行過 `PRAGMA foreign_keys=ON`。
- 存在一筆被別人引用的資料：保管治具、申請排程或借過東西的使用者，或是被 SOP 執行紀錄記著的排程。

## 修正前版本的重現步驟

刪除使用者：

1. 建立一個使用者，再建一個 `keeper_user_id` 指向他的治具。
2. 用 `DELETE /api/auth/users/{id}` 刪掉這個使用者。
3. 重新讀取那個治具。

刪除排程：

1. 建立一筆排程，再建一筆 `schedule_id` 指向它的 SOP 執行紀錄。
2. 用 `DELETE /api/schedules/{id}` 刪掉排程。
3. 重新讀取那筆執行紀錄。

寫進一個從一開始就無效的關聯：

1. 呼叫 `POST /api/fixtures/loans`，`borrower_user_id` 填一個不屬於任何人的值。

## 預期結果

資料庫不會落到自己的 schema 說不可能的狀態：刪除要嘛把引用清乾淨、要嘛被拒絕；
而指名一個不存在借用人的借用紀錄，應該在存進去之前就被擋下。

## 實際結果

三件全部通過。在修正前的版本上實測：

```
修正前 → 使用者已刪除，治具上的保管人 ID 還是： 1 （孤兒）
修正前 → 指向不存在使用者的借用紀錄也寫得進去： 1 筆
排程已刪除，執行紀錄仍指向排程 # 1 → 該排程存在嗎： False
```

API 每次都回成功，任何日誌都沒有東西。

## 證據

- 修正前在應用的 engine 上讀 `PRAGMA foreign_keys` 回傳 `0`；這個開關是每條連線各自設定，而沒有人去設。
- 上面引用的三行是拿真實的 model、在沒有開啟檢查的 in-memory 資料庫上跑出來的——正是修正前的組態。
- `_delete_schedule_db` 處理了三張引用排程的表裡的兩張。第三張 `sop_executions.schedule_id`
  是後來才加的（BUG-009），刪除路徑沒有跟著擴充——讀那個函式就看得到。
- 修正當下掃描開發資料庫，孤兒數為 **0**（`PRAGMA foreign_key_check`），沒有資料需要修補。
  這個缺陷缺的是保證，不是已經造成的損害。

## 根本原因

兩個原因形狀相同：規則寫下來了，但沒有讓它具備約束力。

第一是 SQLite 的預設值。其他資料庫都理所當然地檢查外鍵，所以宣告讀起來就是約束。
在 SQLite 它是惰性的，除非每條連線自己選擇打開，而這個選擇必須掛在「建立連線」那個時機——
寫 model 的時候不會想到的地方。

第二是關聯的清理寫在應用程式碼裡，一條刪除路徑管一條。這在新的引用出現之前都成立：
`sop_executions` 為了報告識別而多了 `schedule_id`（BUG-009），而更早寫好的排程刪除路徑
沒有理由知道這件事。兩者之間沒有任何東西連著，所以漏掉是看不見的。

## 影響

- 刪掉使用者會在治具、借用、排程、訪客 Token 與不可用時段上留下孤兒 ID。
  畫面看起來仍然正常，因為姓名另有文字欄位存著——這正是不會有人察覺的原因。
- 刪掉排程會讓 SOP 執行紀錄指向一筆不存在的排程，而那是測試報告賴以產生的紀錄。
- 借用紀錄可以指名一個從來不是使用者的借用人。
- 全程沒有任何東西大聲失敗，所以損害會安靜累積，很久以後才以「無法解釋的資料」浮現。
- 嚴重度評 Medium 而非 High，是因為受影響的刪除都是低頻的管理動作，而且開發資料庫實測是乾淨的。
  但只要刪掉一筆被引用的資料，**產生**孤兒的機率是 100%。

## 修法

- **啟用檢查**：每條 SQLite 連線現在都會透過 connect 事件執行 `PRAGMA foreign_keys=ON`。
  Alembic 自己的 engine 刻意排除——SQLite 改表等於建新表、複製資料、丟掉舊表再改名，
  開著檢查會擋下這套流程。
- **宣告刪除行為**：十五條外鍵現在各自說明父列被刪時會怎樣。指向使用者的一律清空
  （`SET NULL`）——刪人是管理動作，不該被歷史資料綁住，顯示用的姓名有自己的文字欄位撐著，
  責任追溯留在稽核紀錄。指向治具的一律拒絕（`RESTRICT`），等於把既有的軟刪除規則寫進 schema。
  排程會帶走自己的中間表資料（`CASCADE`），並清空借用與執行紀錄上的排程欄位；步驟紀錄跟著執行紀錄走。
- **升級前的關卡**：migration 動手之前先用 `PRAGMA foreign_key_check` 掃一遍，
  資料庫已經有孤兒就拒絕升級，並指名是哪張表、幾列。它只回報不修補：
  孤兒該清掉還是該追查得看實際資料，這不是 migration 該自己決定的事。
- **明確的拒絕**：指名不存在借用人的借出登記現在回 404「使用者不存在」，
  與隔壁設定治具保管人的端點一致，而不是把外鍵違規變成 500。

有兩個做法考慮過但沒有採用。只在應用程式碼裡處理刪除可以省掉 migration，
但那等於把保證留在已經被證明會漂掉的那一層。把指向使用者的外鍵改成 `RESTRICT`
可以保住「誰確認了這張排程」，代價是只要碰過任何排程的人就再也刪不掉——
而人員管理本來就有「停用」可以讓一個人退場，硬刪是拿來修正誤建資料的。

## 驗證

```bash
cd backend && ../venv/bin/python -m pytest tests/test_foreign_key_enforcement.py tests/test_schema_migrations.py
```

`tests/test_foreign_key_enforcement.py` 釘住原本不存在的五個行為：指向不存在使用者的資料會被當場拒絕；
刪除使用者會清空所有指向他的引用，而資料本身與姓名快照都留著；刪除排程會清空借用與執行紀錄上的排程欄位、
並帶走中間表資料；刪除執行紀錄會一併帶走它的步驟紀錄；還有已經有借用紀錄的治具無法被硬刪。
因為 model 沒有宣告任何 ORM relationship，這些結果都是資料庫在執行 schema，不是 SQLAlchemy 在模仿。

`tests/test_schema_migrations.py` 會在暫存資料庫實跑整條 migration chain，再逐條比對外鍵與 model——
指向哪張表、刪除行為是什麼都比——改了一邊沒改另一邊就會紅。

migration 本身在套用到開發資料庫之前，先在複本上演練過：十五條外鍵正確、四十一個索引沒掉、
列數不變、`foreign_key_check` 乾淨，`downgrade` 也還原得回去。

有一件事沒有涵蓋：升級關卡的「拒絕」路徑是在帶孤兒的複本上人工驗證的，沒有寫成自動測試。
這支 migration 只會對一顆資料庫跑一次，為了證明它而重建一個舊版本的測試，成本高於它保護的東西。
