## 摘要

有兩個彼此獨立的地方，把「以整天為單位表達的期限」當成 UTC 時間軸上的某個瞬間
處理。兩者都讓畫面與操作人員的日曆對不上，最多差一天，而且方向相反。

`due_date` 存的是 naive UTC datetime，這本身是對的。錯的是兩端的轉換：前端把選到
的日期當成 UTC 午夜送出，而摘要端點以 UTC 的日曆日來歸類「今天」。

## 受影響的路徑

| 路徑 | 錯誤行為 |
|---|---|
| `LoanModal.jsx` — 到期日的送出 | 一筆 2026-08-04 到期的借出被存成 `2026-08-04T00:00`，在台北就是 2026-08-04 早上 08:00。從那一刻起該列就變紅、被算進逾期未還，但它其實距離期限還有 16 小時 |
| `fixtures.py` — `GET /api/fixtures/summary` 的 `due_today` | 這個計數用 `today_utc_window()` 歸類。台北 00:00 到 08:00 之間 UTC 日期還停在前一天，所以「今日到期」顯示的是昨天的數字 |

同一個端點的 `overdue` 計數本來就是對的：它比較的是一個瞬間（`due_date < now`），
不帶任何日曆上的歧義。

## 前置條件

- 前端機器的時區早於 UTC（`Asia/Taipei`，UTC+8）。
- 至少有一筆有到期日的有效借出。
- 第二條路徑還需要：觀察者在當地時間 00:00 到 08:00 之間查看左側面板的治具摘要。

## 在修正前的版本上重現

1. 透過借出登記建立一筆借出，到期日設為今天。
2. 過了當地時間 08:00 之後，在治具總表展開該治具的借出子列，會看到到期日以紅色
   顯示並帶有逾期標記。
3. 把前端時鐘設成當地 02:00，重新載入，讀左側面板的「今日到期」數字，拿它跟實際
   在當地日期到期的借出比對。

## 預期結果

- 今天到期的借出，在當地日結束之前都不算逾期。
- 「今日到期」計算的是操作人員當前所在當地日期到期的借出。

## 實際結果

- 該筆借出從到期日當天當地時間 08:00 起就被標成逾期。
- 在 00:00～08:00 這個時段，「今日到期」顯示的是前一個當地日的數字。

## 根因

系統對「只有日期的期限到底是什麼意思」沒有一份共用的答案，於是每個地方各自發明：

- `new Date("2026-08-04").toISOString()` 會把字串解析成 UTC 午夜，於是期限悄悄變成
  「那個 UTC 日的最早瞬間」，而不是「操作人員當地日的最晚瞬間」。
- `today_utc_window()` 以伺服器的 UTC 時鐘建立時間窗，那是後端唯一有的時鐘。對
  伺服器來說這是合理的預設，但那不是操作人員身處的那一天。

兩者都與 [BUG-004](BUG-004-fixture-dates-stored-one-day-early.zh-TW.md) 同一類：
把日曆概念放在 UTC 時間軸上解讀，而不是當地時間軸。

## 影響

- 在到期日當天準時歸還的治具被回報為逾期，逾期未還的數字也把它算進去。由於逾期
  治具正是操作人員會去追的東西，一個誤判就等於一次白跑的詢問。
- 對上早班的人來說，「今日到期」這個數字不可信——而那正是最可能靠它安排一天的
  班別。
- 沒有任何存下來的資料是錯的。兩個缺陷都出在「如何解讀已存下的瞬間」，所以不需要
  更正任何歷史紀錄。

## 解法

- `endOfLocalDay()` 把選到的 `YYYY-MM-DD` 轉成當地日的最後一毫秒；借出登記現在送出
  這個值，而不是 UTC 午夜。後端與逾期的比較刻意維持原樣，因為由排程建立的預約寫的
  是真實的時間戳（排程的結束時間），在那裡套用整天規則反而會把它弄壞。
- `localDayWindow()` 計算當地日的邊界；`ControlCenter` 把它們以 `due_from` /
  `due_to` 傳給 `GET /api/fixtures/summary`，端點再用它們算「今日到期」。沒有帶這
  兩個參數時會退回 UTC 日，所以其他呼叫端的行為維持不變。

## 驗證

```bash
cd client && npm test
cd backend && ../venv/bin/python -m pytest tests/test_fixtures_api.py -v
```

後端的回歸測試有拿修正前的行為驗證過：暫時讓端點忽略那兩個參數，它會以
`0 == 1` 失敗，確認這條測試真的有鑑別力。它的時間窗用固定日期（2026-01-15）而不是
當下日期，所以不會因為剛好在某一天執行而僥倖通過。

前端測試釘在 `Asia/Taipei`，並以凍結在台北 00:30 的時鐘斷言兩個邊界——那是八小時
時間窗裡最糟的時間點。
