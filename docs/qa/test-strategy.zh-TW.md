## 1. 目的

本策略說明 DQA Lab 作為 SW QA／QA Automation 作品時的測試方式。目標不是把功能
全部覆蓋一遍，而是提出可信的證據，證明這個平台守得住風險最高的行為：存取控制、
排程、設備狀態、治具生命週期、維護限制、報告產出，以及跨模組的一致性。

## 2. 品質目標

1. **狀態一致性** — 排程、設備、SOP 執行、治具借出與稽核紀錄，在操作成功與失敗
   之後都必須彼此吻合。
2. **安全限制** — 忙碌中、不可用或維護中的設備不得啟動測試。
3. **存取控制** — 訪客維持唯讀；即使 UI 已經把按鈕藏起來，權威仍在伺服器端的
   授權檢查。
4. **可追溯性** — 重要的狀態變更要留下足夠的資料庫、稽核與測試證據，足以解釋
   發生過什麼事。
5. **韌性** — LINE、AI 與報告產生失敗時，不得破壞核心業務狀態，也不得把該讓人
   知道的錯誤吞掉。
6. **畫面誠實** — 使用者操作之後，畫面必須與後端的權威狀態對得上。

## 3. 範圍

### 在範圍內

- FastAPI 路由、service 層規則、SQLAlchemy 持久化與狀態轉換。
- 排程、維護時段、設備啟停、SOP 執行、治具預約／借出／歸還、授權、稽核、報告、
  AI 帶入排程，以及 WebSocket 支撐的狀態呈現。
- 正向、負向、邊界、故障注入與回歸測試。
- `main` 上的模擬設備 Demo 架構。

### 本基準版本不涵蓋

- 真實試驗箱通訊、廠商協定、序列埠／RS-485 行為，以及實體安全驗證。
- 生產負載、長時間浸泡、滲透、災難復原與多租戶測試。
- 完整的瀏覽器／裝置相容性矩陣。
- 自動化測試中對 Gemini 或 LINE 的實際呼叫。
- 客戶專屬部署與地端基礎設施。

## 4. 測試方法

| 層級 | 目的 | 位置 | 備註 |
|---|---|---|---|
| 靜態檢查 | 在執行前先抓出 Python 品質問題 | `ruff check backend/` | CI 會跑 |
| 後端單元／整合 | 驗證 API、資料庫、service、失敗路徑與狀態機行為 | `backend/tests/` | 使用真實的 in-memory SQLite；跨模組流程會把所有參與的 `SessionLocal` 一起 patch |
| 前端單元 | 驗證前端的確定性工具函式 | `client/src/__tests__/` | Vitest；不做 jsdom 元件測試，關鍵流程改由瀏覽器測試涵蓋 |
| 瀏覽器 E2E | 從使用者視角證明關鍵流程可用 | `tests/e2e/specs/` | Playwright，獨立後端與資料庫，循序執行，不重試 |
| 探索／手動 | 在自動化之前調查新風險並蒐集證據 | 本機 Demo | 確認的缺陷會產出報告，並在可行時補上自動化回歸 |

測試盡可能使用真實的資料庫模型與 service 程式碼。Mock 只保留給外部服務、受控的
故障注入、與時間相關的邊界，以及目前不存在的硬體。

## 5. 環境與測試資料

### CI

GitHub Actions 目前會對推向 `main` 的 push 與以 `main` 為目標的 PR 擋關：

- Ruff
- 後端 pytest
- 前端 Vitest
- Playwright E2E

### E2E

Playwright 使用專屬環境：

- 後端 port `8100`
- SQLite 資料庫 `/tmp/dqa-e2e.db`
- 測試專用帳密與假的外部服務金鑰
- 每個 spec 檔都重建資料庫並重開後端
- 單一 worker、不重試，讓共用狀態造成的缺陷無所遁形

E2E 同樣在 GitHub Actions 上執行（Tests workflow 中的 `e2e` job），失敗時會把
Playwright 報告、trace 與後端 log 上傳為 artifact。由於 HF Spaces 的部署要等
Tests workflow 成功才會啟動，E2E 失敗也會一併擋住部署。

## 6. 風險與執行順序

執行順序由[風險導向測試計畫](risk-based-test-plan.zh-TW.md)決定：

1. P0 — 存取控制、維護排除，以及跨模組的狀態完整性。
2. P1 — 排程衝突與復原、治具庫存，以及 UI 與後端的一致。
3. P2 — AI 帶入排程、報告降級、冒煙測試與周邊 UX。

低優先度的測試不得延誤對 P0 不變量失敗的調查。

## 7. 進入與結束條件

### 進入條件

- 已理解預期行為與失敗的影響。
- 測試資料可以被確定性地建立。
- 外部相依已被 mock 或明確排除。
- 測試不會寫到開發用資料庫。

### 結束條件

- 針對本次變更風險的測試通過。
- 相關的較大範圍套件通過，且沒有無法解釋的失敗。
- 沒有未解決的 Critical 或 High 缺陷影響目標 Demo 流程。
- 已修正的缺陷具備可重現的證據，並在可行時有回歸保護。
- 文件與[追溯表](traceability.zh-TW.md)與實作行為相符。

## 8. 缺陷流程

最低限度的流程是：

`發現 → 重現 → 記錄 → 修正 → 回歸測試 → 驗證`

缺陷報告放在本目錄。Severity 描述影響程度，Priority 描述修復順序。報告必須區分
「觀察到的事實」與「推論」，且在只用模擬器驗證時，不得宣稱已完成實機驗證。

## 9. 目前的限制

- 測試覆蓋率尚未自動發布。
- 在取得硬體與授權協定之前，真實設備行為仍未經驗證。
