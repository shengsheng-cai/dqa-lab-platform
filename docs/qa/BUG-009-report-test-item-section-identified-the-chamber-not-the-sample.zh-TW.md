## 摘要

兩種報告格式都有一個章節，標題寫著「受測樣品資訊 Test Item Information」（CSV）／
「受測樣品 Test Item」（PDF）。這兩節裡沒有任何一個欄位在識別受測樣品。它們實際印出來
的是**試驗箱**——`CH-01`——後面接著測試方法本身的識別資訊。

樣品名稱、案號與客戶其實都在資料庫裡，就在驅動這次測試的那張 `schedules` 資料列上。
沒有任何一項進得了報告，因為 `sop_executions` 沒有外鍵連回 `schedules`——報告端根本
沒有路徑拿到那些資料。

ISO/IEC 17025:2017 §7.8.2.1 列出報告應包含的項目。目前缺六項：(b) 實驗室名稱與地址、
(e) 客戶識別、(g) 受測樣品識別、(h) 樣品接收日期、(l)「結果僅適用於所測樣品」聲明，
以及 (n) 方法的增修或偏離說明。

其中**嚴重的是 (g)**：報告不只是漏掉樣品識別，而是在一個聲稱自己是樣品識別的標題底下，
放了設備識別。

## 受影響的路徑

| 路徑 | 錯誤行為 |
|---|---|
| `reports.py` — `download_csv_report` 第 2 節「受測樣品資訊 Test Item Information」 | 印出設備編號（試驗箱），接著是 SOP ID、測試名稱、測試類型、SOP 版本、參考法規——這些識別的都是**方法**，不是樣品。沒有樣品名稱、沒有案號、沒有客戶 |
| `reports.py` — `_build_pdf` 第 2 節「受測樣品 Test Item」 | 內容相同，漏的也相同 |
| `reports.py` — 第 1 節「報告識別 Report Identification」與報告開頭橫幅 | 開頭只印 `DQA Lab Platform` 這串字，沒有地址；第 1 節則完全沒有實驗室識別。也沒有任何「結果僅適用於所測樣品」的聲明 |
| `models.py` — `SopExecution` | 沒有 `schedule_id`，所以任何一筆執行紀錄都追不回下單的那個案件。這才是讓這個缺漏變成結構性問題、而不只是漏寫一個查詢的原因 |

## 前置條件

無。每一份報告都受影響——不存在任何一組輸入、SOP 或設備，能讓受測樣品那節真的識別到樣品。

## 在修正前的版本上重現

1. 建立一張帶真實案件資料（樣品名稱、案號、申請人）的排程，指派給 `CH-01`。
2. 執行它，或直接為 `CH-01` 灌一筆涵蓋同一時間區間的 `sop_executions` 資料列。
3. 下載該筆執行紀錄的 CSV 或 PDF 報告。
4. 讀第 2 節，也就是標題寫著「受測樣品」的那一節。

## 預期結果

第 2 節要識別出被測的那個東西：至少要有它的名稱、以及它所屬的案號，讓讀者能把「測了什麼」
跟「怎麼測的」分開來看。報告同時也要識別出具報告的實驗室，並聲明結果僅適用於所測樣品。

## 實際結果

第 2 節識別的是試驗箱與方法。以下是對現行版本、在灌好資料的資料庫上實際重現的輸出：

```
============================================================
  2. 受測樣品資訊  Test Item Information
============================================================
  設備編號 Device ID:               CH-01
  SOP ID:                       iec60068_ab_-40_16h
  測試名稱 Test Name:               低溫儲存 Test Ab：-40°C，16 小時（非通電）
  測試類型 Test Type:               chamber
  SOP 版本 SOP Version:           IEC 60068-2-1:2007
  參考法規 Reference:               IEC 60068-2-1:2007 Test Ab
```

當下資料庫裡的案件資料（`MX-1000 工業乙太網路交換器`／`PRJ-2026-0042`／`王小明`）
在報告裡完全沒出現；拿這三個字串各自去比對報告全文，三次都得到 `False`。

而實驗室識別的全部內容，就是報告開頭那段橫幅：

```
  ========================================================
  DQA Lab Platform
  環境測試報告  Environmental Test Report
  ========================================================
```

## 證據

- 受測樣品章節：[`reports.py`](../../backend/app/reports.py)——`download_csv_report`
  第 2 節與 `_build_pdf` 第 2 節，兩者的欄位都是從 `execution.device_id` 與 `sop_data` 組出來的。
- 缺掉的連結：[`models.py`](../../backend/app/models.py)——`SopExecution` 有 `sop_id`、
  `device_id`、`operator`、時間戳與照片路徑，就是沒有 `schedule_id`。
- 該被印出來的資料：[`models.py`](../../backend/app/models.py)——`Schedule.sample_name`、
  `Schedule.project_number`、`Schedule.applicant_name`。
- 重現方式：用一支用完即丟的腳本灌入一張排程加一筆執行紀錄，印出 CSV 報告的第 1、2 節，
  終端機輸出即上方引用的內容。該腳本跑在暫存目錄、刻意不保留；長期的回歸保護會由修正時
  一併加入的測試負責。

## 根因

執行紀錄從來沒有連回下單的那個案件。一列 `sop_executions` 記的是跑了什麼（`sop_id`）、
在哪跑（`device_id`）、誰跑的（`operator`）以及什麼時候跑——全都是關於**這次執行**的資訊。
受測樣品不是執行的屬性，它是**案件**的屬性，而案件在 `schedules` 那張表。兩者之間沒有外鍵，
所以報告端就算想查也無資料可印。

而那個章節標題，是照著「這節應該要有什麼」寫的，不是照著「這節實際拿得到什麼」寫的——
這就是讓一個缺漏變成誤導的原因。

實驗室識別的成因單純得多：開頭那段是當成標題寫的，不是當成 §7.8.2.1(b) 的欄位寫的，
所以它從來沒有長出地址或任何其他識別資訊。

## 影響

- 報告聲稱識別了受測樣品，實際沒有。讀者——包括這份報告要交付的客戶——看到的是一個
  填得滿滿的章節，完全沒有任何線索知道那寫的是試驗箱而不是他的樣品。這比一份明顯空白的
  報告更糟：它錯得很像對的。
- 兩項有現成資料來源的 ISO/IEC 17025 §7.8.2.1「應」列項目（(e) 與 (g)）沒有滿足，
  另外 (b) 與 (l) 只需要固定文字也一樣沒做。
- 這套系統至今產出的每一份報告都受影響。
- 沒有任何存下來的資料是錯的或遺失的。樣品名稱、案號與客戶都還在排程上，缺的只是連結與
  列印，所以不需要更正任何歷史紀錄——修正之後新建的紀錄才會有連結，先前發出的報告需要
  重新產生。

## 解法

- `SopExecution` 加上了 `schedule_id`，型別為可為空、外鍵指向 `schedules`，並寫了一份
  Alembic migration。設為可為空是因為真正的臨時測試本來就沒有案件，那個情況必須表達得出來。
- 兩條啟動路徑（臨時與排程）本來就匯流到同一個地方，而那個地方在有排程時本來就拿得到
  排程，所以直接把欄位填進去。
- 至於測試結束後由 SOP 頁面存下的那一列——也就是使用者實際會去下載報告的那一列——瀏覽器
  並沒有帶任何排程資訊上來。它改成用**同一台設備加上完全相同的測試開始時刻**，去比對測試
  開始時建的那一列，直接繼承那一列的 `schedule_id`。

  這個修法的前一版草稿，是去問「這台設備現在正在跑哪一張排程」。審查時否決了那個做法：
  它是代理指標，不是事實本身。如果人員是在同一台試驗箱已經開始跑下一張排程之後才存檔，
  那個代理指標會把**別的客戶的樣品**掛到這份報告上——那比原本要修的缺陷更糟。繼承開始
  那一列不會有這個問題；認不回來時它就什麼都不給，報告會寫明沒有案件。

  這也是為什麼開始時刻現在只取一次、由設備狀態快取與執行紀錄共用，而不是各自呼叫
  `now()`：差幾微秒就會讓比對無聲失敗，而每一份報告都會安靜地失去樣品識別。有一條測試
  釘住這個不變條件，`.claude/rules/api-conventions.md` 也記下了原因。
- 有連結時，第 2 節印出案件資料。沒有連結時明講沒有，而不是退回去印設備識別：一次沒有
  案件的臨時測試，讀起來就該是沒有案件。
- 以固定文字補上了實驗室識別 (b) 與「結果僅適用於所測樣品」聲明 (l)。實驗室明確標示為
  作品展示用的模擬實驗室、沒有實體地址，而不是掛一個編出來的地址。
- 試驗箱編號從第 2 節移到第 3 節「測試條件」，設備本來就該歸在那裡。第 2 節改名為
  「受測樣品與測試方法」，並把樣品排在方法之前，讓這一節先回答「測了什麼」再回答「怎麼測」。
- (h) 樣品接收日期與 (n) 方法偏離說明**刻意不做**：本 Demo 沒有收樣流程，也沒有方法偏離
  的紀錄，根本沒有資料來源可印。編一份出來會比誠實聲明沒有更糟。

## 驗證

```bash
cd backend && ../venv/bin/python -m pytest tests/test_reports_degradation.py tests/test_schema_migrations.py -v
```

CSV 的斷言直接打在產生出來的報告文字上：有連結的執行紀錄，第 2 節要印出樣品名稱、案號與
客戶，而且那一節不能再出現試驗箱編號；沒有連結的則要印出無案件的說明。另外兩條測試釘住
繼承本身——存下來的紀錄要接到開始那列的案件，而且**不能**接到後來那張排程的案件，後者正是
被否決的做法會犯的錯。

這個機制所依賴的時間戳不變條件被釘了兩次：一次是開始那列與設備狀態快取必須是同一個瞬間，
一次是設備 API 序列化時不能截斷精度。兩條都拿修正前的行為驗證過——把共用瞬間改回各自取值，
第一條會以 27 微秒的差異失敗，那正是這條測試存在的理由。

Migration 對全新資料庫實跑並直接檢查過：欄位、索引與外鍵都能在 SQLite 的批次重建表之後
存活，`downgrade` 也能乾淨回滾。`test_schema_migrations.py` 每次都會涵蓋欄位本身，但不檢查索引。

PDF 的內容**沒有**斷言。要從產生出來的 PDF 取出文字得加一個本專案沒有的解析依賴，為了一條
斷言加依賴並不划算。PDF 與 CSV 共用同一支解析案件的函式，所以資料本身已經被 CSV 的測試釘住，
PDF 這條路徑只有「仍組得出合法 PDF」的煙霧測試。這跟本專案對其他算繪輸出採取的取捨一致。
